# Facilitator Runbook

## The standard of the workshop

The aim is not to make teachers impressed by AI. The aim is to make them **capable, sceptical, safe and useful**. Every demonstration should end with a teacher decision, verification move or school boundary.

## Opening script - first 4 minutes

1. State the boundary before the benefits: training is not permission.
2. Ask participants not to use real people or live school records in exercises.
3. Explain Green / Amber / Red:
   - **Green:** public/non-personal material, low-stakes draft, teacher verifies.
   - **Amber:** school/internal context, assessment/communication, uncertainty about approval or data. Stop and check policy/IBP/DPO route.
   - **Red:** identifiable/sensitive personal data, safeguarding, health/SEN, emotional inference, passwords, unpublished high-stakes assessment, or automated consequential decisions. Do not paste it into an unapproved personal account.
4. Tell them what “success” means: one useful workflow they can repeat safely next week.

## Facilitation rhythm

Use a repeating 6-part rhythm instead of lecturing through slides:

1. **Show** - one concept in 60-90 seconds.
2. **Boundary** - one thing not to do.
3. **Do** - participants try a safe synthetic example.
4. **Verify** - participants find one weakness/error/unsupported assumption.
5. **Rewrite** - improve the prompt or output.
6. **Record** - one line in the booklet.

## Live-route rule

Do not “catch up” by speaking faster. Short courses have a curated live route. The other material is a reference library. If discussion is valuable, skip the next reference slide; do not sacrifice the safety or verification exercise.

## Demonstration rule

For volatile ChatGPT UI, use the v2 UI guide to orient the room, then show the actual live interface. Say explicitly when plan/workspace/rollout differences can move a control.

## The five demonstrations worth protecting

### 1. Bad prompt -> SCOPE-V
Start vague. Rebuild it with Situation, Constraints, Output, Persona, Examples, Verification. Compare the two outputs.

### 2. Fluent but wrong
Use a synthetic task where the model can make a plausible mistake. Ask the room to verify independently before revealing the problem.

### 3. Data boundary
Show a synthetic “named student” prompt and have the room remove identity and unnecessary detail. Do not merely tell them “be careful”. Make them practise the refusal/substitution move.

### 4. Resource production
Create a usable artefact, then run a teacher QA pass: factual correctness, curriculum fit, accessibility, bias, answer key, layout, copyright/source needs.

### 5. Project/workflow design
Show how stable instructions + approved reference files reduce repeated context. Stress that Projects are not a place to dump student work.

## Questions that need escalation rather than improvisation

Use “I can explain the principle; your school must decide the implementation” for:

- “Can I upload our student list?”
- “Can I put an IEP/OPP/SEN plan in?”
- “Can AI grade this summative?”
- “Can we detect AI use reliably?”
- “Can it decide a student's level/stream?”
- “Can I paste a safeguarding disclosure?”
- “Can we connect Drive/Email/Classroom to a personal account?”
- “Does switching off model training make the tool school-approved?”

Then use the school's DPO/IBP/safeguarding/assessment route.

## Closing - last 8 minutes

1. Ask: “What will you try?”
2. Ask: “What will you deliberately not put into ChatGPT?”
3. Ask each participant to name one verification habit.
4. Send booklet.
5. Remind them the certificate records completion/participation, not OpenAI accreditation or legal competence.
6. Give the school leader the 30-day action pack.

## Presenter quality checklist

A strong session contains at least:

- one individual practice;
- one pair discussion;
- one error hunt;
- one data-classification decision;
- one reusable prompt;
- one produced artefact;
- one explicit school-policy handoff;
- one 30-day commitment.
